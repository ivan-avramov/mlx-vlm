## The method — not optional

Six wrong calls were made in the previous session by reasoning from
`git diff --numstat` line counts. They are listed at the end of
`docs/upstream-gaps.md`. Before concluding anything about a hunk:

```bash
git log --oneline -S'<distinctive symbol or literal>' --all -- <path>
git merge-base --is-ancestor <commit> HEAD           # merged-then-dropped?
git merge-base --is-ancestor <commit> upstream/main  # still current upstream?
git show --stat <commit>                             # its WHOLE file set
```

Classify as **DROPPED** (restore), **FORK** (keep), or **STALE** (upstream
replaced it — delete ours). Restoring one file of a multi-file dropped commit is
worse than restoring none: the stale files are internally consistent.

Re-scan at any time:

```bash
python dev/find_dropped_hunks.py       # ranked, with owning commits
```

Lead generator, not an oracle: heavy fork rewrites (`server/generation.py`) show
up as false positives, and so does anything upstream later replaced.

### 5. mRoPE cluster — `a8642018`, `b8671991`, `#1527`, `#1741` — **DONE `540a3189`**

**Land as ONE change including `generate/ar.py`.** Our batcher lacks
`_is_mrope_position_ids_prompt_kwarg`, `_prompt_kwarg_batch_size`,
`_mrope_position_ids_row`, `_concat_prompt_kwarg_rows`,
`_capture_rope_deltas_from_prompt_kwargs`, `_normalize_rope_deltas`. A `(3,B,L)`

So restoring `qwen3_5` alone **creates** a batched-prefill bug. And the sting:
`qwen2_vl`, `qwen2_5_vl`, `qwen3_vl`, `qwen3_vl_moe` are byte-identical to
upstream and already emit `(3,B,L)` through that same broken `ar.py`, so **the
bug is live for those four today** and qwen3_5's staleness is what masks it.

Do **not** re-add `prompt_position_ids` / `language_position_ids` to
`models/base.py` — `b8671991` deleted them upstream and our `base.py` is correct.

Missing pieces: `qwen3_5/language.py` (3-axis decode broadcast, `#1741` chunk
slice, `#1527` `rope_deltas_kw`), `qwen3_5/qwen3_5.py` (request-owned
`position_ids`/`rope_deltas` instead of the stale
`self.language_model._position_ids`), `generate/ar.py`, `server/generation.py`.

**Second-pass verification (still NOT landed — awaiting that decision).** The
claim above is confirmed, and the bug is **worse than described**. All six helpers
are absent (`grep -c "def _is_mrope_position_ids_prompt_kwarg" ... -> 0`, likewise
the other five), and `qwen3_vl/language.py:322` emits exactly
`(3, input_ids.shape[0], input_ids.shape[1])`. Driving our
`_split_prompt_kwargs_per_row` directly:

```
B=2: input (3,2,7) -> per-row [(1,2,7), (1,2,7)]   # want (3,1,7)
B=3: input (3,3,7) -> per-row [(1,3,7), (1,3,7), (1,3,7)]
     row0 == pos[0:1]  ->  True
```

So there are two distinct wrong behaviours, not one:

* **B != 3** — `shape[0] == 3 != batch_size`, so `_prompt_kwarg_row` returns
  `v[:1]`: every row gets the **t axis only**, and mRoPE silently degenerates to
  1-D RoPE for the whole batch.
* **B == 3** — `shape[0] == 3 == batch_size`, so it slices axis 0 *as if it were
  the batch axis*: row 0 gets the t axis, row 1 the h axis, row 2 the w axis, each
  still carrying all three sequences. Completely scrambled positions.

B=1 is safe — `_split_prompt_kwargs_per_row` returns early on `batch_size <= 1`.

Upstream's fix changes `_prompt_kwarg_row`'s **signature** (`(key, v, row_idx,
batch_size)`, upstream:579) so it can special-case `position_ids`, which is why
this cannot be done as an isolated patch to one model.

Confirmed the four qwen VL model directories are byte-identical to upstream
(`git diff --numstat upstream/main -- mlx_vlm/models/{qwen2_vl,qwen2_5_vl,qwen3_vl,qwen3_vl_moe}/`
sums to 0 for each), so nothing on their side masks this — the batcher is the only
broken part, and it is broken for all four today.
